## 第一個可玩目標

兩個真正 Unity Player 加入同一房間。雙方親自決定出兵時間與位置，士兵自行跨橋、尋敵、交戰及攻塔，最後產生雙方一致的勝負與重賽流程。

核心玩法要回答的問題：**玩家能否靠部署位置與出兵時機，用少量兵種形成有效反制和反攻？**

採可持續迭代的獨立遊戲目錄，保留規則、協定與 SDK 接線。路徑／數值試驗放在獨立測試場景或工具；試驗用控制程式不直接成為正式規則。

## 建議首版規則

| 項目 | 首版設定 |
| --- | --- |
| 對戰 | 好友開房 1v1，訪客名稱＋房間碼 |
| 視角 | 直式俯視；自己在下方、戰場填滿手牌上方；平板／橫向只多顯示裝飾場地 |
| 部署 | 手動選牌，點擊或拖曳到己方半場；可與士兵重疊，生成後推開；河道、塔身及場外禁止部署 |
| 自動行為 | 地面士兵自動行進、索敵與攻擊；塔自動攻擊射程內敵兵 |
| 攻擊鎖定 | 第一次出手後維持同一目標直到它死亡；士兵可追出原索敵距離，塔等待鎖定目標回到射程 |
| 主堡開火 | 開局待命，受到傷害或己方任一前塔倒下後永久啟動 |
| 場地 | 目前的一張雙橋地圖，雙方各一座主堡與兩座前塔 |
| 能量 | 初始 5、上限 10；每 3 秒回復 1，最後 60 秒改為每 1.5 秒回復 1 |
| 牌組 | 固定相同 8 張牌，手上 4 張，出牌後循環補牌；起手先採對稱固定配置 |
| 勝利 | 摧毀敵方主堡立即獲勝 |
| 時間 | 正常 3 分鐘；時間到比較已摧毀前塔數，相同則延長 60 秒 |
| 延長賽 | 先摧毀任一敵塔者獲勝；時間到仍未分勝負則平手 |
| 同時結算 | 同 tick 雙方主堡歸零，或延長賽同 tick 雙方破塔，視為平手 |

能量、費用、血量、傷害、射程、攻速及移速均以可調資料配置。這些是本遊戲的測試起點，不是原作數值的宣稱。

## 開發順序與完成條件

### 1. 建立正式工程與雙人連線（已完成）

- 在 `examples/tower-duel/client` 建立受版本控制的 Unity URP 專案，將美術原型接入正式資產目錄；保留既有 GUID。
- 在 `examples/tower-duel/server` 建立獨立 Go 應用，引用現有 GameNetKit SDK。
- 實作訪客、建立／加入房間、兩個席位、雙方就緒與同局 match ID。
- 串好客戶端 session、服務啟停及最短啟動命令。

完成條件：兩個客戶端加入同一房間，取得相同 match／tick 與各自席位；兩端皆以自己的陣營為近端，點擊座標正確轉回伺服器世界座標。

### 2. 一種兵完成端到端流程（已完成）

- 一張測試兵卡、能量回復與部署預覽。
- 伺服器驗證出牌資格、費用與部署範圍；接受後扣費、生成單位。
- 士兵跨橋、接近敵人／建築、攻擊、扣血、死亡與移除。
- 塔攻擊、主堡被摧毀及權威結果同步。

完成條件：兩個真正 Player 可完成一場召兵推塔；移動、傷害、死亡與結果一致。重送同一次出牌不重複扣費或生成。

這是第一個技術里程碑，先用它確認整條資料流與地圖可行。

### 3. 三種兵驗證玩法，補齊基本角色美術（功能／技術驗收完成；待真人試玩）

- 加入盾衛、弓箭手、劍士小隊，建立前排、後排與群體圍攻的差異。
- 為首三種兵挑選同風格免費角色，記錄來源與授權；確認骨架、武器及待機／移動／攻擊／死亡動作。
- 處理橋頭相遇、圍攻、重新索敵、目標死亡、塔身阻擋與局部避讓。
- 對局中顯示能量、費用、兵種辨識、血量與時間，讓玩家能判斷何時增援。

完成條件：玩家能在相近能量投入下，靠兵種搭配、放置位置或等待時機改變交戰結果；雙橋持續交戰不出現長時間卡住。

每輪玩法試驗以 60 分鐘為界，記錄問題後只調整一類變數。由真人試玩後做保留／調整判斷：新玩家能在約 30 秒內主動完成一次部署，並能說出至少一次等待對手出牌後反制的決策。若固定同一種兵一直放就能主導對局，優先修正數值與索敵，再擴充卡池。

### 3.5. 新卡美術盤點與小樣驗證（已整合；待真人可讀性確認）

以已驗收的盾衛、弓箭手與劍士小隊為視覺基準：延續 KayKit 的低面數、圓潤卡通比例、簡潔材質與目前地圖尺度；在正式俯視鏡頭下仍能辨認職能、攻擊與命中範圍。

已從現有免費包採用 Mage、Rogue_Hooded、Barbarian 與對應裝備／動作；火球及冰霜為原創低面數效果。依使用者追加要求，卡面改為八張原創立體卡通插畫，場內模型維持現況，見 [CARD_ART.md](art/CARD_ART.md)。[角色來源清單](art/character-manifest.json) 與 [八張牌美術紀錄](art/EXPANSION_ASSETS.md) 記錄六種兵的來源、面數、動畫及五張新卡的採用方案。

| 新卡 | 要先確認的美術內容 |
| --- | --- |
| 炸彈兵 | 可辨認的角色與炸彈道具、投擲動作、飛行炸彈、爆炸範圍表現與卡面 |
| 突擊兵 | 可辨認的角色／武器、奔跑與衝鋒動作、首次命中表現與卡面 |
| 攻城兵 | 與一般前排有差異的輪廓、裝備、移動／攻塔動作、命中表現與卡面 |
| 火球 | 飛行火球、拖尾、落地爆炸、施法範圍預覽與卡面；可採符合風格的粒子／材質效果 |
| 冰霜 | 施法擴散、持續區域、受影響單位提示、範圍預覽與卡面 |

- 為每張卡記錄候選來源、授權、可沿用素材、缺少內容與採用狀態；新增採用檔案納入可重建的來源紀錄。
- 先做一種新增士兵與一個火球特效小樣，在正式戰場、實際縮放與紅藍兩種視角下驗證；確立共同風格後再擴充其餘素材。
- 士兵檢查骨架、裝備掛點、待機／移動／攻擊／死亡動畫、朝向與縮放；特效檢查命中位置、範圍可讀性、透明材質相容性及多個同時播放的成本。
- 卡面從採用的角色／技能視覺製作，保持與戰場一致。後續建築、飛行兵等新增內容也按批次沿用此流程。

完成條件：五張新卡各有明確的可用來源或製作方案；新增士兵與火球代表小樣通過場內預覽，並記錄待補素材。每張卡進入正式整合前，其模型／動畫／特效須完成對應驗證。資料、協定與手牌循環可同步開發；玩法原型使用的暫代素材要明確標示。

### 4. 完整八張牌與出牌操作（已實作）

新兵種與法術先完成第 3.5 階段的素材確認與對應小樣驗證，再接入正式呈現。

| 卡片 | 角色 | 初始測試費用 |
| --- | --- | --- |
| 盾衛 | 高血量前排 | 3 |
| 劍士小隊 | 三個脆弱近戰單位，圍攻單體 | 3 |
| 弓箭手 | 遠程持續輸出 | 3 |
| 炸彈兵 | 對地範圍傷害 | 4 |
| 突擊兵 | 快速接近、第一次命中有衝鋒效果 | 4 |
| 攻城兵 | 優先攻擊建築，需要護送 | 5 |
| 火球 | 指定範圍傷害 | 4 |
| 冰霜 | 指定範圍減速與降低攻速 | 2 |

- 四張手牌、輪替補牌、費用狀態與下一張預覽。
- 支援滑鼠與觸控拖曳；非法位置、取消操作、等待確認及拒絕原因均有明確回饋。
- 部隊卡限制在己方半場；法術可指定戰場內合法區域。
- 八張插畫卡面分別對應兵種／技能，名稱與費用由 UI 顯示；部署時顯示半透明實際模型或法術作用範圍。

完成條件：八張卡都能正確循環；能量不足、連點、取消、延遲確認與非法落點不造成重複施放或手牌錯位。

### 5. 一整局的遊戲流程（已實作；雙 Player 三局通過）

- 就緒、倒數、正常時間、雙倍回能、延長賽、結算與重賽。
- 結算清楚顯示勝負、破塔數與下一步。
- 離房、對手退出、斷線保留席位及恢復原局。
- 初始重連寬限採 30 秒；期間模擬持續，離線玩家不接收新指令，已出兵的單位持續戰鬥。逾時判負；雙方都逾時則結束並釋放房間。

完成條件：同一組玩家可連續完成三局；離線恢復不重新生成部隊、不重扣費，重賽清除上一局所有狀態。

### 6. 操作呈現、弱網與平台驗收（功能完成；實機／真人待驗收）

- 完成手機直式 HUD、安全邊界、部署區提示、受擊／死亡特效與基本音效。
- 調整近端鏡頭與卡牌操作，使手指不遮住重要落點。
- 依手機與平板參考圖保留完整戰鬥區；滿版畫布與裝飾性外場不增加可部署區，寬畫面壓縮牌區高度。
- 用真正雙 Player 驗收，另建 WebGL 驗證載入、輸入與連線。
- 測試延遲、抖動、重送、重連與慢接收端；區分應用訊息層模擬和實際封包損失。
- 先以雙方合計 80 個單位作壓測目標，量測 tick 耗時、快照大小、流量與 Unity 呈現成本後設定正式上限。超出上限的出牌須明確拒絕且不扣費。

完成條件：提供可啟動的一個 Go 服務與兩個客戶端、一次完整對局證據，以及分開記錄的 Windows／WebGL／實機觸控驗收結果。單位上限與效能依實測報告，不由場景面數推論。

## SDK 與遊戲責任

- Go 擁有能量、手牌、出牌、單位、傷害、塔與勝負；Unity 擁有輸入、預覽、插值、動畫、介面與音效。
- 第一版採 Go 固定 30 Hz、快照 15 Hz 作為量測起點，使用 WebSocket 與完整 JSON。
- 優先使用 SDK 的 loop／transport，以及 Unity core／transport／interpolation。物件生命週期與動作確認按需要接入 replication／actions。
- 每次出牌有與 match／席位關聯的 action ID；伺服器保存確認結果，重送回覆同一結果，避免重複執行。
- 全部公開戰場狀態可以同步給兩端；對手手牌、牌序與能量須在應用投影時隱藏。這項保密與 AOI 是不同責任。
- 尋路與碰撞採 Go 可執行的 XZ 幾何、橋梁導引點與局部避讓；Unity 跟隨權威狀態呈現。地圖與部署規則必須有共用資料與版本驗證。
- 不需要玩家移動預測或射擊回溯；後續若量測顯示同步成本過高，再評估 codec／量化。重播在完整對局穩定後接入。
- 房間、身份與重連組裝可參考 Rumblebound；它們屬於範例應用，不能當作 SDK 已自動提供的塔防功能。

建議目錄：`client`（Unity）、`server`（Go 規則／房間／服務）、`protocol`（協定文件與測試資料）、`art`（素材來源與生成）、`scripts`（啟動／建置／驗收）。

## 優先驗證的錯誤情境

1. 同 action 重送：只生成一次、只扣一次費；新 match 不接受上一局指令。
2. 非法卡牌、費用不足、敵方部署、河道／塔身／場外落點：拒絕且不改狀態。
3. 同 tick 傷害與勝負一致，不由連線或集合遍歷順序決定勝者。
4. 橋面狹窄、雙方大量相遇、追擊目標死亡：單位能重新索敵，不穿塔、不走進河道。
5. 斷線重連、重賽與過期回覆：能量、手牌、單位與結果可恢復，舊局資料不混入新局。
6. 兩端近端視角相反：部署落點與伺服器坐標一致；網路訊息不洩漏對手私有牌組狀態。
